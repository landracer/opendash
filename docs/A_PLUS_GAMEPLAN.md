## 0. How the grading works (so the grades are not magic)

Each category is graded on a fixed rubric. **A = the category's risks are not
just fixed, but *guarded so they cannot silently regress*.** That is the bar:
an A-class category has a test, a CI job, or a docs-lint rule that *fails a
build* when the guarantee breaks. Today only Documentation and parts of
Testing have that property (`scripts/check_docs.sh`, the host test harness).

| Category | Today | Target | Why today's grade | What A-class means here |
|---|---|---|---|---|
| Documentation | A | A+ | Enforced links/headers, honest status culture | Auto-verified numeric claims, threat model, decision log |
| Architecture / Code Quality | B+ | A | Defensive C, but 4.7k-line monolith + pod-pair drift exception | No >1.5k-line UI file, zero documented-exception drift |
| Testing & CI | B | A | Real host tests + 12-node matrix — but see P0.1, the CI claim itself is broken | Coverage gate, fuzz corpus, safety-path coverage |
| Safety Engineering | B− | A | Good interlocks; stale "inhibited" comment on live fire path; unauthenticated wireless arm/deploy | Interlock logic unit-tested in `common/`, authenticated commands, documented + checked threat model |
| Security | C− | A− | No command auth, no OTA signing, open ESP-NOW auto-join | Encrypted fleet, signed OTA or explicit accepted-risk register |
| Repo Hygiene | C+ | A | See §0.1 below | Clone < 200 MB, no tracked file > 5 MB (allow-listed exceptions), CI size-guard |
| **Overall** | **B** | **A / A−** | | |

## 0.2 THE CRITICAL FINDING (blocks everything): the CI claim is false

This is not hygiene — it is a **verification-integrity hole**, and it is why
Phase 0 exists before anything else:

- `common/CMakeLists.txt` (Step 0 comment) and `.github/workflows/build.yml`
  (header notes) both state: *"The generated LVGL C sources under
  fonts/generated/ and images/generated/ are COMMITTED to the repo. CI sets
  OD_PREGENERATED_ASSETS=1 … builds straight from the committed generated
  sources."*
- **Reality, verified 2026-10-06:** `common/fonts/generated/.gitignore`
  contains `*.c` with the comment *"do not commit"* — **0 font `.c` files are
  tracked** (only `opendash_font_config.h`). `common/images/generated/.gitignore`
  likewise ignores `*.c`, `*.h`, `*.bin`.
- Consequence: on a clean CI checkout with `OD_PREGENERATED_ASSETS=1`, the
  converters are skipped and `file(GLOB …)` finds **no font/image sources**.
  Every display node that references the font symbols fails at **link time**.
  "CI builds all 12 nodes green" cannot be true on the current tree.

**Until Phase 0 Task P0.1 lands, no other phase may claim "CI green" as an
acceptance criterion.** Everything downstream inherits this bug.

## PHASE 0 — Verification integrity & hygiene reset (Repo Hygiene C+ → A)

**Effort: 2–3 days. Risk: LOW (one force-push, coordinated). Gate: all later phases.**

### P0.1 — Squash the generated-assets contradiction  ★ DO FIRST
Decide ONE truth. Two options:

- **Option A (recommended): CI runs the converters.** Repo stays slim, the
  `.ttf`/`.png` originals remain the single source of truth, and the nested
  `do not commit` ignore files stay correct.
  1. In `.github/workflows/build.yml` build job, add a prep step:
     `sudo apt-get install -y imagemagick`, `python3 -m pip install Pillow`,
     `npm ci` in `common/fonts` (only if the font converter needs Node — check
     `convert_fonts.py` first), then remove `OD_PREGENERATED_ASSETS` from the
     job env.
  2. Measure one node build once; if the converter cost is acceptable
     (< ~2 min), keep it for all 12 matrix entries.
  3. **Hard-fail guard (the anti-lie mechanism):** in `common/CMakeLists.txt`,
     when `OD_PREGENERATED_ASSETS` IS set, add an explicit
     `if(NOT FONT_SOURCES) message(FATAL_ERROR …) endif()` so a future
     "committed assets" claim can never again be silently false.
- **Option B: actually commit the generated `.c`** via Git LFS
  (~40 MB fonts + image sources), update both nested `.gitignore`s, keep CI
  fast and hermetic. Choose only if CI minutes matter more than repo slimness.

**Acceptance:** a *pristine clone* on a *fresh runner* builds `center` and one
ESP32 controller end-to-end. Evidence: link to the green Actions run.
**Docs to correct regardless of option:** `common/CMakeLists.txt` Step-0
comment, `build.yml` header notes, CHANGELOG Unreleased "CI from zero to real"
entry wording, TODO §1.8 `[x]` sub-item on `OD_PREGENERATED_ASSETS`.

## PHASE 1 — Safety-correctness of the deployment system (Safety B− → A)

**Effort: 1–2 weeks incl. bench time. Risk: MEDIUM (live squib circuits —
bench protocol mandatory). Depends on: Phase 0 (CI trust).**

> **Bench rule for every task in this phase:** fire tests only on a dummy
> load (12 V bulb / buzzer) — never a squib — and record results in
> `docs/safety-deployment-test-checklist.md` as the checklist is extended.

### P1.1 — Fix the stale fire-path comments (30 minutes, do immediately)
`mos-4ch-a/main/main.c` around the parachute dispatch block still says
*"Firing (channel energize) is NOT wired yet — actuator stays inhibited"*
while `parachute_fire()` above it **does** energize channels. Same class of
stale comment near the init log. Correct both in `mos-4ch-a` and `mos-4ch-b`
to describe actual behavior (enabled ∧ mask≠0 ∧ armed → energize; LATCH vs
PULSE; idempotent lockout). Grep both files for `inhibited|NOT wired` and
reconcile every hit.
**Acceptance:** no comment in the two MOS mains contradicts `parachute_fire()`;
review diff line-by-line (safety-critical files — human review, not blind).

### P1.2 — Move the fire interlock into `common/` and table-test it
Today the interlock truth-table lives in `mos-4ch-a/main/main.c` where host tests
cannot reach it — only the config *store* is tested.
1. Add to `common/src/opendash_parachute.c` (+ header): a pure function
   `opendash_parachute_fire_verdict(config, armed, already_fired) -> ALLOW |
   reason-code` — no GPIO, no ESP calls.
2. MOS mains call it before energizing; behavior unchanged (comment-only
   refactor of the decision, action stays at the call site).
3. `test/test_parachute.c` gains the **full truth table**: disabled,
   mask==0, disarmed, already-fired (idempotent), happy-path LATCH,
   happy-path PULSE, hostile config pre-sanitized-then-verdict.
**Acceptance:** CI runs the table on every push; verdict function coverage
100% (gcov — wired in P3.2). This is the A-grade mechanism: the safety
decision becomes testable without hardware, forever.

### P1.3 — Pin control commands to the center's MAC (command authentication, cheap tier)
Any ESP-NOW peer that can reach a MOS/relay node can currently `SET_ARM` /
`DEPLOY` / relay-switch it. The learn-the-center-MAC machinery already exists
in `dispatch_message()` (MOS mains learn the center from genuine center→node
unicast only). Extend it into a policy gate:
- **control-class opcodes** (parachute 0x27..0x29 family, relay set, boost
  control, OTA trigger) accepted **only** from the pinned center MAC;
  otherwise drop, increment a `ctrl_rejected` counter, log at WARN with
  `MAC2STR` of the offender;
- **telemetry-class opcodes** keep current behavior (push from registered
  peers);
- pin is NVS-persisted; re-pairing requires a boot-button press on the node
  (physical presence) — mirrors how the OTA button-gate already works.
**Acceptance:** bench test — a second ESP32 blasting DEPLOY frames changes
nothing on the MOS node and the reject counter ticks; documented as a new
checklist item with pass/fail recorded.

### P1.4 — Fleet ESP-NOW encryption (LMK) — the real fix for the RF threat model
Encrypt every peer with a fleet LMK (same PMK on all 12 nodes):
- `esp_now_set_pmk()` + `encrypt=true` on every peer add (patch
  `common/src/opendash_espnow.c` — currently `encrypt = false` in both the
  broadcast and unicast peer paths — plus each node's local peer adds);
- key storage: NVS blob `wifi/lmk` with a **compile-time default key** for
  first boot (dev fleet), overridable per-car via an id-key procedure later;
- **rollout is atomic:** old and new firmware cannot talk (plaintext vs
  encrypted) — so this ships as ONE fleet re-flash event, same ritual as the
  2026-10-06 round-2 bring-up (all 11 nodes, one sitting, heartbeat-probe
  after). Write the runbook first (`wiki/ota-bluetooth.md` style), dry-run on
  two spare boards, then the whole fleet.
- **Brick-recovery:** BLE OTA is unaffected (separate radio path) — verified
  in the current code; note it in the runbook.
**Acceptance:** mixed-key frame is rejected on the wire (verify with the
second ESP32 from P1.3); all 11 nodes re-probe `Center: ONLINE`/heartbeat OK.

### P1.5 — Auto-disarm on center silence (DECISION NEEDED from owner)
A MOS node armed by the center keeps its arm even if the center dies. Options:
(a) keep current semantics (arm survives radio loss — argues for physical
master-kill design), (b) auto-DISARM after N seconds without a center
heartbeat (proposed N = 30 s, heartbeat already exists via node_health).
This is a *racing-safety philosophy* call: recommend (b) + document why.
**Acceptance:** chosen behavior implemented, unit-tested via the virtual clock
in `test_node_health.c`-style harness, and written into
`wiki/safety-deployment-system.md` with the rationale.

### P1.6 — Deploy confirmation UX + threat model paragraph
Center UI manual-DEPLOY becomes two-step (arm-confirm modal with channel mask
echo). The safety docs gain a "Wireless trust model" section: what an attacker
within radio range could do **before** P1.3/P1.4 and the explicit statement
that post-P1.4 the fleet assumes a hostile RF environment.
**Acceptance:** checklist doc extended; bench run of the full updated
checklist recorded with dates.

**PHASE 1 DONE =** interlock table-tested in CI; DEPLOY from foreign MAC
impossible (bench-proven); fleet encrypted; stale comments gone; checklist
extended and executed on the bench.

## PHASE 2 — Security posture (C− → A−)

**Effort: ~1 week. Depends on: P1.3/P1.4 (shared plumbing). A− not A: full
secure-boot is optional-but-listed; accepted risks must be *registered*, not
ignored.**

### P2.1 — Threat model document (docs/security.md — planned new file)
One page, four sections: assets (fleet control, squib circuits, OTA path,
driver data), attackers (pit-lane RF bystander, borrowed laptop, evil-flash),
current controls after P1.3/P1.4, and an **accepted-risk register** with
re-review dates. Link it from `readme.md` Quick Links and PROJECT_INDEX doc
tables (docs-lint will keep those links honest).

### P2.2 — OTA provenance: signed apps
- Enable `CONFIG_APP_SIGNING` (esp_app_format signing) with a project key;
  `ble_ota.py` unchanged (it still ships the .bin, which now carries the
  signature block); the bootloader's `CONFIG_SECURE_BOOT` decision is recorded
  as an option with a **prose decision + date** in the security doc: for a
  private vehicle fleet, app-signing alone often is the right cost/benefit —
  what is *not* acceptable is silence.
- Remove the `esp_ota_set_boot_partition` "verify = integrity-only" ambiguity
  from the docs: BLE_OTA.md states exactly what is and isn't checked.
**Acceptance:** unsigned .bin rejected by a signed-fleet node (bench-proven,
logged in checklist).

### P2.3 — BLE access control decision
Choose: (a) keep open-but-button-gated OTA + register the risk, or (b) NimBLE
whitelist/bonding of the owner's phone/laptop. Recommend (a) now, (b) if OTA
over public networks ever becomes routine. Document the choice.

### P2.4 — Secret handling rules
- One home for the LMK: NVS + compile-time default; **never** per-copy
  one-off keys scattered in sdkconfigs;
- `sdkconfig*` audit: grep for any stray PSK/passphrase before each release
  (add a line to `scripts/check_docs.sh`: fail on `CONFIG_ESP_WPA`-style
  secrets or `lmk`-like hex blobs in tracked files);
- key rotation = one documented page (re-flash PMK fleet-wide — same ritual
  as P1.4 rollout).

**PHASE 2 DONE =** signed firmware accepted end-to-end on the fleet, unsigned
rejected on the bench, threat model published in-repo, secrets rule enforced.

## PHASE 3 — Testing & verification (B → A)

**Effort: ~1 week rolling. Depends on: P0.1 (CI must be real). Grows out of

### P3.1 — Fuzz the two parsers (host-side)
`opendash_msg_deserialize()` and the MD UART frame parser are the only two
attacker-controlled byte sinks in the system. Add `test/test_fuzz_parsers.c`:

seed committed; occasional corpus additions from any real-world bad frame
(capture format already exists in DATAFLOW failure-mode table).
**Acceptance:** runs in the unit-tests CI job, < 5 s.

### P3.2 — Coverage gate
`-coverage` flags on the host build, `gcovr` summary job step: enforce
**≥ 80% lines on the pure-logic files** (`opendash_protocol.c`,
`node_health.c`, `opendash_parachute*.c`, `opendash_data_model.c`,
`channel_management.c` once tested). Start at today's actual number, ratchet
up. Report per-file in the CI job log.

### P3.3 — Untested-logic backlog (in priority order)
1. `channel_management.c` — queue-full drop-oldest, channel routing
   invariants (DATAFLOW §8 failure modes become named tests);
2. boost config clamp/sanitize (mirror of parachute sanitize tests);
3. `opendash_layout_store` layout serialize/restore round-trip;
4. odometer rollover/persistence.

### P3.4 — Batch fan-out replay simulator (TODO §1.8's own open item)

the actual production data path, not just the codec.

### P3.5 — Nightly hardware-in-loop (stretch, optional for A)
A bench Pi with the shared FTDI + a serial capture rig, `od-flash.py` smoke +
